ETAPA 1 • FUNDAMENTOS

Antes de falar de Git: o que é versionamento?

Nesta primeira etapa, vamos partir do início. Você não precisa conhecer Git, GitHub ou qualquer ferramenta de versionamento. Primeiro precisamos entender um problema comum: um arquivo muda ao longo do tempo.

Ideia principal: quando modificamos um arquivo, criamos um novo estado daquele arquivo. Esse novo estado pode ser entendido como uma nova versão.

1. O que é uma versão?

Uma versão é um estado de um arquivo ou projeto em determinado momento. Sempre que fazemos uma alteração importante, podemos considerar que surgiu uma nova versão.

Versão 1 página criada
→
Versão 2 título alterado
→
Versão 3 menu adicionado
→
Versão 4 erro corrigido
Exemplo simples:
Você criou um arquivo chamado index.html. Depois acrescentou um título. Em seguida criou um menu. Depois corrigiu um erro no rodapé. O mesmo arquivo passou por diferentes estados. Cada estado representa um momento da evolução do projeto.

2. O que significa versionar?

Versionar significa manter um controle organizado dessas diferentes versões. Em vez de guardar apenas o arquivo atual, registramos a evolução do projeto para saber o que mudou, quando mudou e qual era o estado anterior.

3. Então, o que é versionamento?

Definição:
Versionamento é o processo de controlar e registrar as diferentes versões de arquivos ou de um projeto ao longo do tempo.

Esse controle permite acompanhar as alterações realizadas e, quando necessário, recuperar uma versão anterior.

4. Como fazemos isso sem um sistema de versionamento?

Antes de conhecer uma ferramenta específica, imagine uma forma manual de guardar versões. Muitas pessoas fazem várias cópias do mesmo arquivo:

📁 projeto-site
📄 site.html
📄 site-novo.html
📄 site-final.html
📄 site-final-corrigido.html
📄 site-final-agora-vai.html
Esse método até pode funcionar em projetos muito pequenos, mas rapidamente gera confusão. Qual arquivo é realmente o mais recente? O que mudou entre site-final.html e site-final-corrigido.html? E se precisarmos recuperar apenas uma alteração feita dias atrás?

5. Que problemas o versionamento ajuda a resolver?

Perder uma versão Uma alteração nova pode substituir algo que funcionava anteriormente.
Não saber o que mudou Sem histórico, fica difícil identificar quais alterações foram realizadas.
Muitas cópias Arquivos como final, final2 e final-corrigido tornam o projeto confuso.
Trabalho em equipe Duas pessoas podem alterar os mesmos arquivos sem saber o que a outra fez.

6. O que um sistema de controle de versão faz?

Um sistema de controle de versão é uma ferramenta criada para organizar esse processo. Em vez de depender de várias cópias de arquivos, ele mantém um histórico estruturado das mudanças.

Registra o histórico Permite acompanhar a evolução do projeto ao longo do tempo.
Identifica alterações Ajuda a verificar quais arquivos foram modificados.
Permite recuperar versões Se uma mudança causar problema, podemos consultar ou recuperar um estado anterior.
Ajuda na colaboração Organiza as alterações feitas por diferentes pessoas em um mesmo projeto.

7. Exemplo completo

1
Primeira versão

O aluno cria a estrutura básica de uma página HTML.

2
Segunda versão

Ele adiciona um cabeçalho e um menu de navegação.

3
Terceira versão

Ele cria um formulário de contato.

4
Problema

Uma alteração no CSS deixa o menu quebrado.

5
Uso do histórico

Com o versionamento, é possível consultar como o projeto estava antes do erro e identificar a mudança realizada.

Guarde esta ideia:
Versionamento não é “Git”. Versionamento é o conceito de controlar as mudanças e versões de um projeto. Na próxima etapa conheceremos ferramentas usadas para aplicar esse conceito.

ETAPA 2

Git e GitHub não são a mesma coisa

Os dois aparecem juntos com frequência, mas têm funções diferentes. O Git controla versões. O GitHub hospeda repositórios Git na internet e oferece recursos de colaboração.

Git É um sistema de controle de versão distribuído. Ele funciona no computador e registra o histórico do projeto.
GitHub É uma plataforma online que hospeda repositórios Git e permite compartilhar, revisar e colaborar.

ETAPA 3

Prepare o ambiente

Para começar, você precisa do Git instalado e de um terminal. Pode usar Git Bash, PowerShell, terminal do VS Code ou outro terminal de sua preferência.

1. Verifique a instalação

git --version

2. Configure seu nome e e-mail

git config --global user.name "Seu Nome"
git config --global user.email "seuemail@exemplo.com"

3. Confira a configuração

git config --list
Atenção: o nome e o e-mail configurados ficam associados aos commits. Em computadores compartilhados do laboratório, confira sempre a configuração antes de iniciar.
Atividade 3 — Preparação:
Execute os três passos acima. Registre uma captura de tela mostrando o resultado de git --version e outra mostrando seu nome configurado.
ETAPA 4

Crie seu primeiro repositório

Um repositório Git é uma pasta cujo histórico passa a ser controlado pelo Git. Vamos criar um pequeno projeto web para praticar.

📁 meu-primeiro-repositorio
📄 index.html
📄 style.css

Passo 1 — Crie a pasta

mkdir meu-primeiro-repositorio
cd meu-primeiro-repositorio

Passo 2 — Inicie o Git

git init
Depois do git init, o Git cria uma pasta oculta chamada .git. É nela que ficam informações usadas para controlar o histórico do repositório.

Passo 3 — Veja o estado do projeto

git status
Atividade 4 — Primeiro repositório:
Crie index.html com um título e um parágrafo. Crie também style.css e aplique uma cor ao título. Em seguida, execute git status. Observe como o Git identifica arquivos ainda não rastreados.

ETAPA 6

Commits: registre mudanças com clareza

Um commit representa um ponto do histórico do projeto. Uma boa mensagem deve ajudar outra pessoa a entender rapidamente o que foi alterado.

Mensagem fraca git commit -m "alterações"
Não explica o que mudou.
Mensagem melhor git commit -m "Adiciona formulário de contato"
Indica a mudança realizada.
1
Faça uma mudança pequena e coerente.

Evite misturar correção de CSS, criação de página e alteração de formulário no mesmo commit quando forem tarefas diferentes.

2
Confira com git status e git diff.

Veja exatamente o que mudou antes de registrar.

3
Adicione e faça o commit.

Use uma mensagem curta, objetiva e relacionada à alteração.

ETAPA 7

Branches e merge

Uma branch é uma linha de desenvolvimento. Ela permite testar ou criar uma funcionalidade sem alterar diretamente a linha principal do projeto.

mainprojeto estável
↘
feature-contatonova funcionalidade
↗
mergeunião das mudanças
git branch
git switch -c feature-contato

# faça alterações e crie um commit

git switch main
git merge feature-contato
git branchLista as branches existentes.
git switch -c nomeCria uma nova branch e muda para ela.
git switch mainVolta para a branch principal.
git merge nomeIntegra outra branch à branch atual.
Um conflito pode acontecer quando duas alterações incompatíveis atingem a mesma parte de um arquivo. O Git marca o conflito e alguém precisa decidir como o conteúdo ficará.
Atividade 7 — Trabalho isolado:
Crie a branch feature-menu. Nela, adicione um menu de navegação no HTML, faça um commit e depois volte para main. Por fim, use git merge feature-menu.
ETAPA 8

Conecte o projeto ao GitHub

Até aqui o histórico está apenas no computador. Agora vamos conectar o repositório local a um repositório remoto hospedado no GitHub.

  1. 1
    Crie um repositório no GitHub.

    Use um nome simples, por exemplo curso-git.

  2. 2
    Copie a URL do repositório.

    Ela será usada para cadastrar o remoto.

  3. 3
    Conecte o projeto local.

    Cadastre o endereço remoto com o nome origin.

  4. 4
    Envie os commits.

    Use git push.

git remote add origin https://github.com/SEU-USUARIO/curso-git.git
git branch -M main
git push -u origin main
origin é apenas um nome usado normalmente para identificar o repositório remoto principal.
git remote -vMostra os repositórios remotos configurados.
git pushEnvia commits locais para o remoto.
git pullBusca e integra alterações do remoto na branch atual.
Atividade 8 — Publicação:
Crie um repositório no GitHub e publique seu projeto. Depois, abra a página do repositório e confirme se os arquivos e commits aparecem.

ETAPA 10

.gitignore e boas práticas

Nem todo arquivo deve ser enviado ao repositório. Arquivos temporários, dependências baixadas ou informações sensíveis devem ser avaliados antes de entrar no histórico.

Exemplo de .gitignore

node_modules/
.env
dist/
.vscode/
*.log
node_modules/Dependências que podem ser reinstaladas com o gerenciador de pacotes.
.envPode conter senhas, tokens e configurações privadas.
*.logArquivos de log geralmente não precisam entrar no versionamento.

Boas práticas

Nunca coloque senhas, tokens de API ou chaves privadas em commits públicos. Mesmo que o arquivo seja apagado depois, a informação pode continuar no histórico.
Atividade 10 — Preparando um projeto real:
Crie um arquivo .gitignore no seu projeto. Se o projeto for apenas HTML/CSS/JS, inclua pelo menos arquivos de log e uma pasta de testes locais. Se for Node.js, inclua node_modules/.
